mcp-context-card 1.10

A project's AGENTS.md, memory and identity over MCP, and the card that shows them

Release · Nov 28, 2026 · Blog

AGENTS.md is a file in a repository. An agent that reaches a project over MCP has no working directory, so it has no way to find that file. mcp-context-card is an MCP server that gives the agent three things: the project's AGENTS.md, facts it remembers across sessions, and an identity. Clients can discover all three through the Server Card and an AI Catalog, and people can read them as a business card.

It's MIT, on npm and in the MCP Registry as io.github.Wolfe-Jam/mcp-context-card. Run it as the only MCP server in a host, or alongside the ones you already have.

What it does

  • Context. read_agents_md serves AGENTS.md whole or one section at a time, so a client can pull ## Test without reading the whole file. author_agents_md drafts one from the repo's facts if you don't have one.
  • Memory. remember, recall and forget keep facts in a file, so they survive a restart.
  • Identity. whoami reads the project's .fafa, falling back to package.json.
  • The card. The same sources, drawn as a business card: the front has the name, the kind and version, and a one-liner. Flip it for About, Context, Memory and Discovery. It comes in light or dark. In a host that supports MCP Apps, the card is drawn in the chat; everywhere else you get it as Markdown.
  • Discovery. A Server Card at /mcp/server-card with one _meta key per concern, and an AI Catalog at /.well-known/ai-catalog.json listing the card and the files beside it.

That's 10 tools, all annotated (7 read-only), and one prompt, show.

New in 1.10

AI Catalog v0.9 ids

Each catalog entry is named urn:air:{domain}:{name}-{kind}, for example urn:air:example.com:my-project-context. The domain comes from the project's .fafa. One segment after the domain can't be read the wrong way round: v0.9 reads it as a name with no kind. If you published catalogs from an earlier version of this server, set MCP_CONTEXT_CARD_FORMER_IDS=1 and each entry records its old id.

Only a host you vouch for

Over HTTP, the card and the catalog include the server's own address. Up to 1.10.1 that address came from the request, and any client can send a Host or X-Forwarded-Host header. Discovery responses are cached as public for an hour, so one request could put someone else's domain in a cached catalog.

From 1.10.2, the server names only a host it can vouch for: loopback on a local bind, or a name you list in MCP_CONTEXT_CARD_ALLOWED_HOSTS. For any other host, the card has no remotes and the catalog uses relative URLs, the same as the static file in the repo. A proxy's X-Forwarded-Host counts only for a listed name, and responses carry Vary on the headers the address comes from.

UPGRADE: a deploy reached by a public name lists it in MCP_CONTEXT_CARD_ALLOWED_HOSTS.Without it, the card and catalog name no host. The server says so at start.

Every catalog URL resolves

The catalog lists only files the server actually serves: no AGENTS.md, no context entry. Relative URLs are written relative to the catalog itself (../AGENTS.md), so they resolve both when served and in a repo browser.

Try it

terminal, in your project folder

# your project's card, in the browser
npx mcp-context-card card

# Claude Code; then: show context card
claude mcp add contextcard \
  -- npx -y mcp-context-card

Most hosts take the same command in their mcpServers config. The README has goose, Cursor and the HTTP setup.

How it was checked

1.10.2 had six rounds of independent review before release, each on the fixes from the round before. Every round found something, and the most useful findings were in my own fixes. One example: the second round changed the rule to "a forwarded host that isn't allowed takes its forwarded protocol with it". The third round showed that this let any client downgrade a listed deploy to http, just by adding a bogus header.

TRIED: a fix from a review is new code. It gets reviewed too.

Each code fix came with a test that fails without it: 281 tests in all, on Linux, macOS and Windows with Node 22 and 24. Before the publish, the packed tarball was installed cold and run over stdio and HTTP. After it, a stranger's install from npm checked the published version.
