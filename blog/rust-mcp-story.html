An MCP Story about Rust

From zero to 104 Rust servers in the official MCP Registry

Story · Oct 30, 2026 · Blog

How it was

At the start of 2026, the official MCP Registry knew how to list a server published to npm, PyPI, NuGet, Docker (OCI), or as an MCP bundle. It did not know crates.io.

So a Rust MCP server had no proper way in. You could wrap your binary in a bundle and list that, which is what my own server, rust-faf-mcp, did at first (0.2.2, as an mcpb). It worked, but it meant every Rust server pretended to be something else, and a client couldn't run it the way Rust developers install things: cargo install.

The hole

The registry decides which package types it trusts. For each one, it has a small validator that checks the person publishing really owns the package. npm, PyPI, and the others had one. Cargo didn't, so the door was shut for the whole Rust ecosystem.

The offer

On March 12, I opened an issue: Support crates.io as a package registry type (#1055).

Six weeks later, Radoslav Dimitrov, one of the registry's core maintainers, answered:

"Good idea. Rust is a gap worth closing, crates.io is a legitimate ecosystem."

He pointed to the registry's guide for adding a package type. That was the offer: here's how, go and do it.

The work

Rado said yes on April 24. The pull request was up two days later, on April 26.

The registry is written in Go, so the work was Go, not Rust. The guide has the steps: add the type to the server.json schema, write a validator, and add tests and docs.

The validator proves ownership in two calls to crates.io's own API: ask where the crate's README lives, fetch it, and look for a line that says mcp-name: <your server's name>. Only the crate's owner can put that line there.

Most of the work was testing. The validator is 160 lines of Go. The tests beside it are 411, and they run against the real crates.io, not a mock. Well-known crates like serde, tokio, and rand have to be rejected, because they carry no mcp-name line. Four kinds of wrong registry address have to be refused. Server names in every format the registry allows have to pass.

The proof was a real server. I had built rust-faf-mcp in early March, so the validator had something live to check, and shipping it found a trap that only cargo has: crates.io strips HTML comments when it renders a README. The hidden mcp-name line that works on PyPI and NuGet simply vanishes. Version 0.3.0 went out with an invisible token; 0.3.1 fixed it, and the registry's docs now warn every cargo author about it.

Then five weeks of review. P4ST4S checked the two-call flow against live crates.io and asked for more: a self-contained positive test, a live test anchored on a real published crate, and proper handling when crates.io itself has an error. By June 1, every point was answered: 19 of 19 cargo tests passing, the lint clean, 10 files and 671 lines, including the docs.

It was also my first contribution to the registry: someone from outside adding a whole new package type to the official one. It took some balls. Rado knows what went into it.

The merge

Rado merged #1207 on June 3. The next two days, he hardened it himself: a safer README fetch, clearer status handling, and stronger tests (#1330, #1331).

On July 13, it shipped to production in registry v1.8.0. The release notes read: "add cargo (crates.io) as a package registry type", with a line marking it as my first contribution. Four days later, rust-faf-mcp was listed as a cargo package.

What followed

The same day as the merge, a second piece went live: a hosted version of the server, with its tools written in Rust and compiled to WebAssembly, running on Cloudflare's edge at mcpaas.live/rust. Same tools, no install.

In August, I sent one more small PR, #1511, adding cargo and crates.io to the schema's examples so the docs matched what the registry already did. Rado merged it three days later.

The add-ons

  • npx. From 0.4.1 (August 8), the server is also on npm, as a small wrapper. So the registry lists it twice, as cargo and as npm, and anyone with Node can run npx rust-faf-mcp without a Rust toolchain.
  • A name of its own. From 0.4.0, it's listed as one.faf/rust-faf-mcp, proven by DNS instead of a GitHub account.
  • The basics, done properly. It builds on the Rust version it declares, builds in Docker, and from 0.8.3, --version and --help answer instead of starting the server.

The latest

This week a check caught something. The same project.faf scored 30% on the hosted Rust server and 9% everywhere else. The hosted worker was on an older SDK. Nothing looked broken: it answered, and the number looked reasonable. Only putting one file through every surface showed it.

I moved it to the current kernel and added a test that pins the numbers. Today, the same file scores the same on all four surfaces: the CLI, the native Rust server, the hosted Rust server, and the hosted TypeScript server.

The outcome

Today, the official registry lists 104 active servers published as cargo packages, the first on July 13 and the latest on October 30: 109 days. One is mine (my old name is one of 2 more, now deprecated). 103 are other people's Rust servers: databases, SSH, Obsidian, Godot, Moodle, security tools, code search, tools for coding agents, and more. Some ship as cargo and npm together, as does mine.

For scale: NuGet (.NET), supported much longer, lists 165 servers to cargo's 106 (both counts include deprecated ones). And the pace is rising: 15 new active cargo servers in July, 20 in August, 27 in September, 42 in October.

None of those 103 needed me. They needed the door open.

The future

  • The official Rust SDK still can't target WebAssembly. Everyone running Rust MCP on the edge, myself included, works around it. Once that lands, the edge becomes the easy path for Rust servers.
  • Same input, every surface. The check that caught this week's drift is a habit anyone can copy. Any server that runs in more than one place can drift the same way.
  • More doors. The guide that let cargo in is open to the next ecosystem that's missing.
